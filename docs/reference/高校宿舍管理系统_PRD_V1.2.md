## 1. 项目概述

### 1.1 项目背景

高校宿舍管理中，报修申请和维修进度可能依赖线下沟通，卫生检查分数可能分散在纸质表格或电子表格中，学生难以及时查看结果，管理方也难以进行跨周/月、跨楼栋的卫生状况分析。本项目通过统一的宿舍管理系统，实现基础住宿信息维护、报修处理、学生会宿管部卫生评分录入，以及卫生评分与排名可视化。

### 1.2 产品定位与目标

面向高校内部学生、学生会宿管部成员、维修人员和系统管理员的轻量化宿舍管理系统。

核心目标：
1. 让学生可以线上报修并追踪处理进度。
2. 让学生会宿管部成员通过一个账号连续录入**多个寝室**的卫生评分。
3. 让系统自动计算综合得分、周期统计、排行榜及低分提醒。
4. 让学生查看自己寝室的评分和报修进度，让管理人员获取可信的统计结果。
5. 在合理的本科毕设工作量内体现完整业务流程、数据库建模、权限控制与数据分析能力。

### 1.3 已确认需求与明确排除项

**已确认**
- 宿舍管理员即学生会宿管部成员，**两者是同一角色**。
- 一个宿舍管理员账号可以给多个寝室评分，支持连续录入。
- 卫生评价包括评分标准、多维评分、自动综合计算、周/月统计、排行榜、低分整改提醒。
- 报修管理保留申请、分配、处理和进度追踪。
- **卫生检查每周固定进行**；按周创建检查批次，记录各寝室的完成/未完成情况。
- **所有宿舍管理员账号均可对全校任意寝室评分**，不设置楼栋数据范围限制。
- **普通学生仅查看自己当前所在楼栋的卫生排行榜**，可查看本寝室成绩和历史趋势。
- **系统仅提供电脑浏览器访问的 Web 页面**，不要求适配手机屏幕，不开发独立 App 或微信小程序。

**明确不做**
- 报修后的满意度评价、星级评价。
- 通知公告模块中的宿舍公告发布、公告阅读等功能。

**本期不纳入（控制毕设范围）**
- AI 故障识别、智能派单、复杂宿舍自动分配算法。
- 在线支付、访客管理、门禁/物联网设备、实时聊天、短信推送。
- 独立的学生会负责人审批角色与复杂审核流。

## 2. 第一性原理：业务对象与必需闭环

系统核心围绕三个事实建立：
- **住宿归属**：某名学生在某一时间归属于某间寝室；评分属于寝室而非单个学生。
- **问题处理**：报修必须从提交走到处理结果，可回溯责任人、时间和状态。
- **卫生事实**：每次检查是一次带有检查对象、评分人、检查时间和当时评分标准的不可随意篡改的记录；排名是对有效检查数据计算得到的视图。

因此最小可运行闭环为：
1. 管理员创建楼栋、房间、学生及其住宿关系。
2. 学生提交报修 → 宿舍管理员分配维修人员 → 维修人员处理 → 工单完成。
3. 系统管理员设置卫生评分标准 → 每周创建固定检查批次 → 学生会宿管部成员从全校寝室中选择并逐间评分 → 保存记录 → 系统自动计算与展示周/月趋势、排名、低分整改提醒。

## 3. 用户角色与权限

| 角色 | 基础信息 | 报修 | 卫生评分 | 统计和整改 |
|---|---|---|---|---|
| 系统管理员 | 管理账号、楼栋、房间、学生和入住关系 | 查看全部、必要时管理工单 | 配置标准、查看全部记录、纠错 | 全局看板、阈值配置、整改管理 |
| 宿舍管理员（学生会宿管部成员） | 查看工作所需的宿舍信息 | 接收并分配工单、查看进度 | 可对**全校任意多个寝室**录入评分、查看自己录入的记录 | 查看全校卫生统计和待整改记录 |
| 普通学生 | 查看本人和当前寝室基本信息 | 提交报修、查看自己提交的工单及状态 | 查看本寝室已发布的检查成绩 | 查看本寝室历史趋势、**仅当前所在楼栋排行榜** |
| 维修人员 | 查看必要的任务位置 | 查看被分配工单、更新进度及完成记录 | 无 | 无 |

权限规则：
- 权限校验在服务端执行，不能仅靠前端隐藏按钮。
- 学生只能查询自己拥有权限的工单及所在寝室的非敏感信息。
- 维修人员只处理分配给自己的工单。
- 宿舍管理员（学生会宿管部）可以对全校任意寝室录入卫生评分；该权限仍须在服务端校验账号角色与状态，不设置按楼栋限制。
- 评分标准只允许系统管理员修改；已产生的历史检查记录保留当时的评分标准快照。
- 已正式提交的检查记录不可无痕覆盖，需保留修改原因与审计日志；V1.1 不设置多级审批。

## 4. 功能需求

### 4.1 F01 用户、权限与基础宿舍信息管理（P0）

| 编号 | 功能 | 验收标准 |
|---|---|---|
| F01-01 | 账号登录/退出 | 有效账号登录成功；禁用账号无法登录 |
| F01-02 | 基于角色的访问控制 | 越权接口请求返回拒绝，不泄露数据 |
| F01-03 | 楼栋、楼层、寝室管理 | 支持增改查、启停；寝室编号在同一楼栋内唯一 |
| F01-04 | 学生与住宿关系 | 学生可关联一个当前有效床位/寝室；不允许同一床位同时分配多人 |
| F01-05 | 维修人员、宿舍管理员账号维护 | 角色设置和启停生效，操作留痕 |

建议管理端提供列表、条件搜索、分页和常用表单；批量导入 Excel 可作为 P2 可选项。

### 4.2 F02 宿舍报修管理（P0）

**参与者**：学生、宿舍管理员（学生会宿管部）、维修人员、系统管理员。

**主流程**：
1. 学生在自己寝室发起报修，填写问题类型、文字描述，可上传图片。
2. 新工单进入“待分配”；宿舍管理员选择维修人员分配任务。
3. 维修人员查看工单，标记“处理中”，记录处理说明。
4. 维修人员完成后标记“已完成”，学生可查看处理结果。
5. 如误报或未处理前不再需要维修，可按权限取消工单并填写原因。

**状态**：`待分配 → 待处理 → 处理中 → 已完成`；`待分配/待处理 → 已取消`（按授权角色和业务限制）。

| 编号 | 功能 | 验收标准 |
|---|---|---|
| F02-01 | 创建报修单 | 自动绑定提交人及当前寝室，必填类型和描述 |
| F02-02 | 图片附件 | 支持规定格式和大小的图片；校验文件类型与权限 |
| F02-03 | 分配维修人员 | 只允许有权角色分配；记录分配人和时间 |
| F02-04 | 工单状态流转 | 服务端检查允许的状态迁移，不可跳转非法状态 |
| F02-05 | 工单查询与进度 | 学生查看自己的工单；维修人员只看分配给自己的工单 |
| F02-06 | 处理记录 | 每次状态变化保存操作者、时间、必要备注 |

**不做**：维修满意度评价、星级打分、自动智能派单。

### 4.3 F03 卫生检查评分标准管理（P0）

管理员维护评分方案。默认示例方案（可配置）：

| 维度 | 权重 | 分数范围 |
|---|---:|---|
| 地面卫生 | 40% | 0–100 |
| 物品摆放 | 30% | 0–100 |
| 环境整洁 | 30% | 0–100 |

规则：
- 支持添加、编辑、启停维度，配置名称、显示顺序、权重。
- 启用评分方案的权重合计必须为 100%。
- 各维度成绩必须在 0–100 范围内，允许小数位数统一设置（本期建议整数）。
- 方案变更需生成新版本，不能反向改动已提交记录的历史计算结果。

### 4.4 F04 宿舍管理员连续录入多寝室评分（P0）

**核心场景**：学生会宿管部成员登录后，进入本周固定检查批次，按楼栋/房号检索全校寝室，在一个界面中连续为多个寝室评分。

交互和规则：
1. 进入本周检查批次，选择楼栋及寝室；支持检索全校所有楼栋与房间，或按房间号顺序跳转。每周检查批次的所属周由检查日期确定。
2. 按当期启用方案填写各评分维度，实时展示加权总分。
3. 点击“保存并下一间”，当前寝室评分提交成功后进入下一寝室；保存失败不跳转并保留表单输入。
4. 显示“本周已录入 X 间 / 待录入 Y 间”进度列表；可按楼栋筛选，本周应检宿舍为当前有效寝室清单（空置寝室是否参与检查由系统管理员配置，默认仅在住寝室）。
5. 再次评分时明确提示是否为重复提交。**同一周固定检查批次内同一寝室仅一条有效正式记录**；不同周允许重复检查。需要补检的宿舍在同周原批次完成，不另建重复正式评分。
6. 每条记录必须保存 `room_id`、`inspector_id`、`inspection_date`、`batch_id`、各项分值、权重快照、总分、提交时间。
7. 若需要改错，授权账号进行“更正”，填写原因、保留修改前后值及操作人，不直接覆盖历史痕迹。

默认**提交即生效，不设负责人审批**；是否增加“草稿暂存”可作为 P1 功能。

**固定周检安排（V1.1 确认）**：
- 系统每周有且只有一个默认正式检查批次，以 ISO 周为键（周一至周日）；管理员可在该周开始前创建，或系统首次录分时自动创建。
- 统计“应检寝室数、已检寝室数、未检寝室数、完成率”；未检寝室显示“未检查”，不得直接按 0 分计入均分或排行榜。
- 周检允许在一周内分多次录入、多账号分别录入不同寝室；同寝室重复正式提交由服务端唯一约束阻止。
- 若学校存在节假日停检，系统管理员可以将该周标记为“停检”，不参与周检完成率考核；该设置不改变“每周固定检查”的默认组织方式。

### 4.5 F05 卫生综合评分、周/月统计和排行榜（P0）

**单次综合得分**：

\[
S = \sum_{i=1}^{n} w_i s_i, \quad \sum_{i=1}^{n}w_i = 1
\]

其中 `w_i` 是第 `i` 项权重，`s_i` 是对应得分，最终得分建议保留 2 位小数。后端负责权威计算，前端的实时分数仅供预览。

**周期统计**：
- 周：采用 ISO 周（周一至周日），按**周固定检查批次**归属；月：自然月，使用当月各周检查的有效记录。跨月周检的归属月份以检查批次的检查日期为准。
- 周成绩：默认取当周批次唯一有效正式评分；月成绩：默认取归属当月的各周有效正式评分的算术平均值。未检查/停检周不按 0 分处理。
- 需要达到最低有效检查次数（默认 1 次）才进入排行榜；未达次数显示“未检查/数据不足”，不计为 0 分。月排名须展示各宿舍实际参与周次数，以便识别缺检。
- 同一周期同分并列排名，明确采用并列规则（本期使用竞赛排名，例如 1、1、3）。
- 支持楼栋、周期、寝室筛选；显示样本次数和周期成绩，防止误解。
- **学生排行榜查询范围固定为本人当前所在楼栋**，且仅显示该楼栋寝室编号、周期得分和名次，不显示个人姓名等非必要信息；即使修改查询参数也不能查看其他楼栋排行。系统管理员与宿舍管理员可查看全校、分楼栋数据。

**可视化**：
- 楼栋平均成绩柱状图。
- 寝室周/月成绩趋势折线图。
- 卫生维度平均分对比图。
- 宿舍排行榜列表或柱状图。
- 低分宿舍数量/比例与待整改数量统计。

数据口径须一致：图表、排行榜、导出（如有）均基于同一套后端统计规则。

### 4.6 F06 低分提醒与整改闭环（P1，建议做）

**默认触发策略**（可配置）：
- 单次检查总分低于 60 分，生成“待整改”记录；
- 或连续两次有效检查低于 60 分时生成提醒（推荐最终只启用一种主规则，避免重复整改单）。

工作流程：
`检查触发规则 → 产生待整改记录 → 管理员跟进 → 复查或核实 → 关闭整改`。

要求：
- 同寝室、同一连续整改事件不重复生成多个未关闭记录。
- 每条整改记录关联触发它的检查记录，显示触发原因。
- 本期“提醒”表现为系统内列表和状态提示，**不包含宿舍公告或短信/微信推送**。
- 低分阈值和触发规则仅系统管理员可配置。

## 5. 关键业务规则

| 规则编号 | 规则 | 目的 |
|---|---|---|
| BR-01 | 同一楼栋下寝室编号唯一 | 防止房间身份混淆 |
| BR-02 | 同一时刻一个床位仅一个有效入住关系 | 防止分配冲突 |
| BR-03 | 评分维度权重之和必须为 100% | 防止总分失真 |
| BR-04 | 同一 ISO 周默认一个正式检查批次；同一批次同一寝室仅一条当前有效正式评分记录 | 防止重复计分 |
| BR-05 | 评分记录包含评分人、日期、时间、评分方案版本 | 可追溯 |
| BR-06 | 评分标准更新不影响历史结果 | 可比性与审计 |
| BR-07 | 无检查记录不等于 0 分 | 防止错误排名 |
| BR-08 | 报修状态迁移由服务端约束 | 防止非法操作 |
| BR-09 | 宿舍管理员可评分全校寝室；学生仅可查看本楼栋排行及本寝室成绩 | 数据安全 |
| BR-10 | 评分更正保留原因和变更记录 | 数据可信 |
| BR-11 | 每周固定检查；未检按未检查标识，不作为零分 | 避免统计误导 |
| BR-12 | Web 页面仅需适配桌面电脑浏览器，不要求移动端响应式布局 | 终端一致性 |

## 6. 页面规划

- 我的待处理工单、工单详情、维修状态更新。

## 7. 数据模型（概念层）

| `inspection_scheme` | 评分方案 ID、版本、启用状态、生效时间 |
| `inspection_criterion` | 方案 ID、维度名称、权重、顺序 |
| `inspection_batch` | 批次 ID、ISO 周所属年份与周号、检查日期、状态（待检/进行中/完成/停检），同一 ISO 年-周唯一 |
| `inspection_record` | 记录 ID、批次 ID、寝室 ID、评分人 ID、综合得分、提交时间、状态 |
| `inspection_score_detail` | 记录 ID、指标名称及权重快照、实际分数 |
| `inspection_revision_log` | 评分记录 ID、修改人、修改原因、修改前后值、时间 |
| `rectification_record` | 寝室 ID、触发检查记录 ID、状态、原因、处理时间 |
| `operation_log` | 关键管理操作人、时间、对象和行为 |

核心关系：
- 一栋楼包含多间寝室，一间寝室可存在多条不同时段的检查记录。
- 一个学生会宿管部账号可以为**全校任意寝室**创建多条不同周的检查记录；**不需要“一账号只能对应一寝室”或按楼栋限制**。
- 一个检查记录包含多个维度分数明细。
- 一个学生可以创建多张报修单，一张报修单在当前版本分配一位负责人。

## 8. 非功能需求

### 8.1 性能
- 毕设演示规模建议以约 5,000 名学生、1,000 间寝室、全年数万条评分记录为模拟测试数据（**仅测试规模假设，并非实际学校数据**）。
- 常规列表查询在测试环境下目标 P95 小于 2 秒，统计看板查询目标 P95 小于 3 秒；需记录测试硬件和数据规模。
- 列表分页，评分记录按日期、寝室和检查批次建立适当索引。

### 8.2 安全
- 密码使用可靠的单向哈希算法（如 BCrypt），不可明文存储。
- 服务端 RBAC 权限控制和数据范围校验。
- 文件上传格式、大小、权限校验；避免任意文件上传。
- 关键操作审计，敏感资料最小化呈现。
- 开发/论文展示采用脱敏或模拟数据，不公开真实学生信息。

### 8.3 可靠性与体验
- 工单状态切换、评分保存必须事务化，防止部分写入。
- 对重复评分并发提交使用唯一约束及明确错误提示。
- 连续评分切换时，保存失败须保留当前输入。
- **电脑端 Web 适配**：保证主流桌面浏览器下报修、连续评分录入、成绩查询和维修处理可正常使用；建议以 1920×1080 为主要设计尺寸，同时兼顾 1366×768 等常见电脑分辨率。

## 10. 关键验收场景

| 用例 | 操作 | 预期结果 |
|---|---|---|
| AT-01 | 宿舍管理员依次评分 A101、A102、B201 | 同一账号可跨楼栋保存三条不同寝室记录；评分人一致、寝室 ID 不同 |
| AT-02 | A101 在同一检查批次再次提交 | 阻止重复正式评分，提示查看或发起更正 |
| AT-03 | 修改评分标准权重 | 仅新版本生效，历史得分和维度快照不变 |
| AT-04 | 仅一个维度未填写时点击提交 | 阻止提交并指出缺失项 |
| AT-05 | 某寝室当周没有检查 | 显示“无数据/未达参评次数”，不计 0 分 |
| AT-06 | 同分宿舍排行 | 按配置的并列规则返回一致名次 |
| AT-07 | 非授权人员尝试调用评分修改接口 | 服务端拒绝并保留必要安全日志 |
| AT-08 | 学生报修、宿舍管理员派单、维修人员处理 | 工单正确流转至已完成，有完整操作轨迹 |
| AT-09 | 维修人员尝试处理不属于自己的工单 | 服务端拒绝 |
| AT-10 | 卫生评分低于触发阈值 | 产生或更新待整改记录，不产生宿舍公告 |
| AT-11 | 评分保存时网络失败 | 页面保留表单数据，提示重试，不误切到下一间 |
| AT-12 | 进入一个新 ISO 周的固定检查 | 创建或打开该周唯一批次；列出应检/已检/未检数并计算完成率 |
| AT-13 | 本周 A101 未检查，其他寝室已检查 | A101 显示未检查、不记零分、不进入周排名 |
| AT-14 | A 栋学生请求查询 B 栋排行（含篡改 API 参数） | 服务端拒绝越权查询，学生只可查看 A 栋排行 |
| AT-15 | 宿管部账号选择 A 栋与 B 栋寝室评分 | 两个楼栋的评分都可正常提交，均需满足唯一批次和评分规则 |
| AT-16 | 使用 1920×1080 和 1366×768 的桌面浏览器访问 | 核心操作均可正常使用，主要表格、表单和图表无影响操作的遮挡或溢出 |

## 11. 开发优先级与范围控制

### P0：必须交付
1. 登录和四类角色权限。
2. 学生、楼栋、寝室及住宿关系管理。
3. 完整报修工单处理流程，不含评价。
4. 评分标准配置及快照版本。
5. 学生会宿管部成员在每周固定检查批次中连续为**全校任意多个寝室**评分。
6. 综合分数、周/月成绩、卫生排行与趋势图。
7. 基础安全检查及关键场景测试。

### P1：推荐交付
1. 低分整改记录及闭环。
2. 评分更正及修改审计。
3. 评分录入进度与草稿暂存。

### P2：时间充足再考虑
1. Excel 批量导入基础信息。
2. 卫生数据报表导出。
3. 独立 App 或微信小程序（不在 V1.2 开发范围内，若日后扩展需另立需求）。

**范围冻结原则**：优先完成评分业务闭环、排名口径一致性、权限与测试，再考虑外部 AI 能力或其他全新模块。

## 13. 毕设论文可呈现的特色与实验

### 13.1 项目亮点
- **面向学生会宿管部的多寝室连续评分工作流**：减少逐寝室反复进出页面的操作负担。
- **可配置的多维度加权卫生评价模型**：支持评分标准版本与历史记录快照。
- **可解释的统计与排名机制**：处理检查次数不一致、缺失记录、同分并列等实际情况。
- **低分发现到整改复查的闭环**：把分数展示扩展为管理动作。

上述是应用场景和业务设计创新，**不应宣称加权平均或 ECharts 为原创算法**。

### 13.2 建议实验与测试
- 多寝室连续评分与逐间独立页面录入的操作步数/完成时间对比（记录测试条件）。
- 10/100/1000 间寝室及不同检查记录量下的统计查询耗时。
- 对权重变更、缺检、重复记录、同分并列等边界情况编写自动化测试。
- 对不同阈值设置下的低分提醒数量进行对比分析，不以模拟结果冒充真实学校效果。

## 14. 已确认决策与剩余默认假设

### 14.1 已确认决策（V1.2）

1. **卫生检查频率**：每周固定检查；系统按 ISO 周组织唯一正式检查批次，并展示未检名单与完成率。
2. **宿舍管理员评分范围**：所有学生会宿管部账号可评分全校任意寝室，同一账号可以连续录入多间；不配置楼栋范围限制。
3. **普通学生的排行榜**：仅查看本人**当前所在楼栋**的排行榜；本寝室评分明细和历史趋势可查看。服务端根据住宿关系限定范围。
4. **终端形态**：仅电脑端 Web，通过桌面浏览器访问；不要求手机端响应式布局，也不开发独立微信小程序。

### 14.2 不阻塞开发的默认业务假设

以下未获单独确认，沿用 V1.1 原有默认方案：

1. **评分发布与纠错**：提交立即生效，无负责人复核；更正需记录原因和变更日志。
2. **报修派单责任**：宿舍管理员（学生会宿管部）负责分配维修人员；若真实学校流程不同，可在开发前调整授权，不改变评分功能。
3. **每周应检范围**：默认所有当前有学生入住的寝室，空寝室不计入应检总数；节假日可由系统管理员设置停检周。
4. **月度成绩口径**：按归属当月各周有效评分算术平均，未检查不记零分，展示参与周次数。
5. **低分整改**：保留 V1.0 的推荐 P1 功能，默认系统内提示、不做公告和消息推送。

上述是明确可执行的默认值；如导师或实际学校管理制度另有规定，可作为后续版本变更。

## 15. 成功验收标准

在本地/演示环境中，使用至少四类测试账号和模拟寝室数据，能够完整演示：
1. 学生登录并提交报修，查看状态；宿舍管理员派单；维修人员完成处理。
2. 学生会宿管部成员使用**同一个账号**连续为至少三个不同寝室评分，且能跨楼栋评分。
3. 系统按每周固定检查生成唯一正式批次、检查进度和未检名单，依据可配置维度和权重计算综合分，跨周/月统计正确。
4. 触发低分整改时可以查询对应记录。
5. 非授权角色无法操作受限数据，历史评分标准变更不会改变已保存记录。
6. 学生仅能访问自己所在楼栋排行榜；电脑端浏览器可完成所有关键业务操作。
7. 页面完整、可部署，有数据库设计、接口说明、测试记录和论文所需截图。

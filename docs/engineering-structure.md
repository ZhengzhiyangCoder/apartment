# 工程文件结构 V1.0

日期：2026-11-11。状态：**用户已确认，V1.0 定稿**。本文是后续开发的工程结构基准，业务工程尚未创建。

## 1. 已确认边界

- 用户接受：同一个仓库，一个 Maven 后端工程、一个 Vue 前端工程，四类角色共用前端。
- 用户明确：前后端分离，毕设只需本地运行，不需要云服务器部署。
- 沿用批准方案：Java 17 / Spring Boot / Spring Security / MyBatis-Plus，Vue 3 / TypeScript / Element Plus / ECharts，MySQL 8；后端单体按业务模块组织，同源 Session 与 CSRF 防护。
- 第一版 Neumorphism 原型是唯一界面基准。Spec V1.0 已在后续审核中定稿，正式实现尚未启动。
- 用户已接受下文的模块职责、目录分层、配置与测试位置，并确认按推荐的本地启动方案定稿。

## 3. 后端：先分业务，再在业务内分层

```text
backend/
├── pom.xml
├── mvnw / mvnw.cmd / .mvn/      # Maven Wrapper，具体版本实施时锁定
└── src/
    ├── main/
    │   ├── java/com/example/apartment/
    │   │   ├── ApartmentApplication.java
    │   │   ├── config/           # 全局框架配置
    │   │   ├── common/           # 通用响应、分页、异常等小范围基础类型
    │   │   ├── support/
    │   │   │   ├── audit/        # 关键操作审计记录及授权查询
    │   │   │   └── storage/      # 本地文件读写；访问权限由业务校验
    │   │   └── modules/
    │   │       ├── identity/     # 登录、Session、角色、账号、密码与账号资料
    │   │       ├── housing/      # 学生资料、楼栋、寝室、床位、住宿关系与历史
    │   │       ├── hygiene/      # 方案、批次、应检名单、草稿、评分、更正、整改、统计
    │   │       ├── repair/       # 工单、派单、处理、图片关联与状态日志
    │   │       └── dashboard/    # 按角色汇总已有业务数据
    │   └── resources/
    │       ├── application.yml
    │       ├── application-local.yml
    │       ├── mapper/           # 按业务分目录存放确有需要的 Mapper XML
    │       ├── db/migration/     # 按版本维护结构与必要基础数据迁移
    │       └── db/demo/          # 显式加载的模拟演示数据，与结构迁移分开
    └── test/
        ├── java/com/example/apartment/  # 按模块放置规则及真实 MySQL 集成测试
        └── resources/                  # 独立测试配置与最小测试数据
```

以 `repair/` 为例，内部按需建立 `controller/`、`service/`、`mapper/`、`entity/`、`dto/`。Controller 接收请求、做输入校验并调用服务；Service 执行业务规则与事务；Mapper 处理数据库访问；Entity 表达持久化对象；DTO 定义接口输入与输出。客户端不直接使用数据库实体作为接口契约。

先采用直接的业务服务类，不为每个类额外制造接口、实现类和转换层。模块中的评分计算、工单状态流转等规则需要独立表达时再提取类；目录只在实际使用时建立。

### 数据归属和协作边界

| 模块 | 负责的数据与规则 | 跨模块协作 |
|---|---|---|
| identity | 登录凭据、账号状态、角色、个人账号资料与密码 | 通过受控账号查询供其他模块校验操作者或维修人员；学生学籍资料由 housing 管理 |
| housing | 楼栋、寝室、床位、学生资料、当前住宿和历史 | 提供当前住宿、寝室与楼栋范围等查询；学生资料关联账号，不保存第二套密码或角色 |
| hygiene | 方案版本、周检、名单快照、草稿、正式评分、更正、整改、周/月排行与趋势 | 读取住宿信息确定范围；创建批次时固定应检名单；管理自己的分数、统计规则及更正记录 |
| repair | 工单、提交时位置、派单、状态、处理说明与图片元数据 | 从 housing 获取提交时寝室；从 identity 校验维修人员；使用 storage 保存受控图片 |
| dashboard | 工作台待办与统计汇总 | 调用各业务模块的查询能力，应用相同权限；不再存一套工单、成绩或入住事实 |

共同规则：

- 跨模块通过明确的业务服务或只读查询结果协作，不直接修改其他模块的表，也不在 Controller 中调用其他模块的 Mapper。
- 跨模块用例由对应的应用服务编排，统一事务；不引入远程服务或消息队列。具体服务依赖在接口设计时检查，避免循环依赖。
- `common/` 不接收评分、派单、入住等业务规则；`support/` 只承担跨业务支持能力，业务状态日志和评分更正明细仍归各自模块。
- 登录、角色与数据范围在服务端校验。前端隐藏菜单不能代替权限判断；图片文件不能由静态目录绕过工单权限直接提供。
- 账号创建涉及学生资料时需要一致的结果；停用账号、楼栋、寝室或床位前，按已确认规则校验当前入住和未完业务。维修人员停用也不能跳过未完工单约束。
- 调寝后，成绩和排行读取新的当前住宿范围；历史报修仍保留提交时寝室；已经固定的应检名单不因调寝自动重算。

## 4. 前端：业务页面共用，角色控制入口与操作

```text
frontend/
├── package.json / package-lock.json
├── index.html
├── vite.config.ts               # 本地开发与构建配置，版本实施时核验锁定
├── tsconfig.json
├── playwright.config.ts         # 指向本工程的 e2e/，使用本地真实服务
├── public/                      # 可公开静态资源，不放报修图片
├── src/
│   ├── main.ts / App.vue
│   ├── router/                  # 路由与角色入口
│   ├── layouts/                 # 共用侧栏、顶栏、内容框架
│   ├── components/              # 被多个业务实际复用的界面组件
│   ├── styles/                  # 第一版的颜色、阴影、间距等样式变量与全局样式
│   ├── lib/                     # HTTP 请求、日期与格式化等基础能力
│   └── features/
│       ├── identity/            # 登录、个人账号、账号管理与会话状态
│       ├── housing/             # 住宿管理及学生“我的住宿”
│       ├── hygiene/             # 卫生管理、评分、整改及学生成绩/排行
│       ├── repair/              # 管理工单、我的报修、我的维修任务
│       ├── dashboard/          # 四角色工作台
│       └── audit/              # 有权角色的操作审计查询入口
└── e2e/                        # 登录权限、报修流转、评分、调寝等浏览器测试
```

业务目录内按需放 `pages/`、`components/`、`api.ts`、`types.ts` 及少量复杂逻辑。组件和规则测试靠近被测文件。不同角色需要不同页面时，在所属业务下设置页面；例如学生新报修与宿管派单可以使用不同页面，但共用工单详情、状态和请求封装。

后端响应作为业务事实来源；前端只保存会话展示信息、筛选条件和编辑状态。评分草稿按正式需求使用后端持久化。原型用于视觉与交互参考，其内存演示数据和权限模拟不直接替代正式业务逻辑。

## 5. 本地运行方案

默认本地启动三个部分：

```text
浏览器 → Vue 本地开发服务（页面与 /api 代理）→ Spring Boot → MySQL 项目容器
                                                  └→ .runtime/ 下的受控图片
```

- 前端由本机 Node/npm 启动，后端由本机 Java/Maven 启动；前端单独构建，不把页面打入后端 JAR。
- 浏览器通过同一个前端入口访问页面与 `/api`，由开发代理转发请求；后端继续使用既定 Session、HttpOnly Cookie 与 CSRF 机制。
- Compose 默认只启动隔离的 MySQL 容器和专用持久化卷；后端配置通过环境变量接收数据库连接与文件存储目录。
- 本地服务使用回环地址，具体端口在实现前检查占用并写入说明。停止服务保留数据库与上传文件，普通启动不重置演示数据。
- 本地毕设演示沿用这套运行方式；当前不把 Nginx、云服务器、域名或 HTTPS 证书列为交付要求。
- 如后续用户需要“所有组件一条 Compose 命令启动”，可再增加对应配置；当前不把它作为已确认交付。

具体依赖版本、端口和启动命令在实现阶段核验与锁定。当前只完成方案确认，启动方案尚未执行验证。

## 6. 配置、数据和验证约定

- `application*.yml` 保存可公开配置与环境变量占位；真实密码和本机路径通过本地环境配置注入，实际 `.env`、`.runtime/`、构建产物和依赖目录不纳入版本管理。
- 结构变化以 `db/migration/` 中的版本迁移为执行来源，数据库文档同步解释；不维护另一套会与迁移分歧的建表脚本。
- 演示数据显式加载到项目指定数据库，初始账号说明写入 `docs/demo.md`。测试数据库与演示数据库隔离，不能让测试清理日常演示数据。
- 后端测试覆盖权限、状态流转、计分、事务和并发；需要数据库的验证使用真实 MySQL。前端测试关注必要交互与显示逻辑；`frontend/e2e/` 覆盖跨角色真实流程。
- 启动脚本只管理本项目资源，需提供明确的停止方式；系统软件缺失、权限或跨目录写入问题按已有协作约定处理。
- 文档随真实实现更新，测试报告区分已执行结果、未验证环境和已知限制；不声明 Windows 等尚未验证环境可用。

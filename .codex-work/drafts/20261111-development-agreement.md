## 1. 用户已确认

- Codex 主导系统整体开发，用户协助必要操作。
- 不根据假定工期裁剪范围，不需要教学式讲解。
- 沿用附件业务范围：电脑端 Web、系统管理员/宿舍管理员（学生会宿管部）/学生/维修人员四角色；宿管部可跨楼栋连续评分，学生只能查看当前楼栋排行。
- 需求来源：[PRD V1.2](../../docs/reference/高校宿舍管理系统_PRD_V1.2.md)、[数据库设计 V1.0](../../docs/reference/高校宿舍管理系统_数据库设计与ER图_V1.0.md)。原资料副本保留原文，本稿明确其实施口径。

## 2. 推荐交付范围

完成 PRD 的 P0 与 P1：

1. 登录/退出、四角色权限、账号维护、个人资料与密码修改。
2. 楼栋、寝室、床位、学生资料及入住/调寝/退宿管理，保留住宿历史。
3. 学生报修与图片、宿管派单、维修处理、进度查询、取消及状态日志。
4. 评分方案与版本、每周检查批次、固定应检名单、检查进度、未检名单。
5. 跨楼栋连续评分、保存并下一间、输入校验、草稿暂存、防重复与并发保护。
6. 正式评分的授权更正、原因与修改前后审计。
7. 周/月统计、排行榜、卫生维度对比、寝室趋势及管理看板。
8. 低分整改列表、跟进、核实与关闭。
9. 模拟数据与四类演示账号、数据库建表/迁移文件、接口说明、运行/部署说明、测试记录及演示步骤。

检查进度正式归入核心验收；整改和更正不再作为首版可省略项。完整论文正文不在本轮软件开发交付内，交付可用于论文的设计与测试材料。

附件 P2 的 Excel 批量导入、报表导出和新增终端保留为后续扩展；附件明确排除的公告、维修评价、AI 派单、支付、聊天和短信不扩入本期。

## 3. 推荐实现与运行方式

- 后端：Java 17、Spring Boot、Spring Security、MyBatis-Plus；单体应用按业务模块组织。
- 前端：Vue 3、TypeScript、Element Plus、ECharts；中文桌面界面，兼顾 1920×1080 与 1366×768。
- 数据库：MySQL 8 系列；以附件 18 张核心表为设计输入，为服务端草稿等已纳入功能补充必要结构，所有调整写入正式数据库设计与迁移文件。
- 登录：同源部署的服务端 Session，使用 HttpOnly Cookie 和 CSRF 防护；账号禁用与数据范围由服务端校验。
- 附件：后端受控本地存储，元数据入库，读取时校验工单权限；不接入额外对象存储服务。
- 数据库运行：优先复用已有 Docker，使用本项目隔离的 MySQL 容器和专用数据卷；不覆盖或接入不明用途的既有数据库。
- 本地开发采用 Maven/npm，交付可复现的依赖版本、环境变量示例、启动说明与 Docker Compose 部署配置。
- 本轮验收目标是本机可实际运行并验证，另提供部署配置；不自动购买服务器、域名或发布到公网。
- 依赖版本在实施阶段按官方兼容关系确定并锁定。项目所需依赖及容器镜像需下载；系统级软件缺失时先说明具体安装项，不擅自替换已有环境。

## 4. 账户、住宿与数据可见范围

- 账号由系统管理员创建/重置，不开放匿名注册；一个账号一个角色，账号禁用后不得继续调用业务接口。
- 学生资料可保留未入住状态：可登录并查看个人信息及自己提交过的报修；未入住时不能新报修、查看寝室成绩或楼栋排行。
- 一名学生最多一个当前床位，一个床位最多一名当前入住学生；调寝必须同时结束旧关系并建立新关系。
- 有历史业务引用的账号/楼栋/寝室/床位不硬删除；停用前校验当前入住和未完业务，必要时先迁移或处理。
- 学生的成绩、趋势、排行榜按当前寝室及当前楼栋限定。调寝后不能继续查询旧寝室成绩；自己提交的历史报修仍可查看，工单位置保留提交时寝室。
- 排行展示寝室编号、成绩、参评次数和名次，不披露学生姓名；宿管部和系统管理员可查看全校及楼栋统计。

## 5. 报修边界

- 工单初始为待分配：待分配 → 待处理 → 处理中 → 已完成。
- 宿管部负责派单；系统管理员可必要时管理工单。只有启用的维修账号可被分配，维修人员只能操作自己的工单。
- 待处理阶段允许有权管理角色重新分配并记录原因；进入处理中后不提供普通重分配。
- 学生可取消自己尚未进入处理中的工单；宿管部和系统管理员也可按同样状态约束取消，均需填写原因。
- 已完成、已取消为终态；新问题重新提交，不静默重开旧单。完成维修需处理说明。
- 图片限定 JPG/PNG/WebP，单张不超过 5 MB、每单最多 5 张；校验真实文件内容并仅向有工单访问权的账号提供图片。

## 6. 周检、统计与版本规则

| 议题 | 推荐统一口径 |
|---|---|
| 周与时区 | 业务时间采用 Asia/Shanghai，周按 ISO 周一至周日；跨年使用 ISO 年周组合。 |
| 创建批次 | 首次进入当前周检查时自动创建，管理员可主动创建当前周；不额外提供提前创建未来批次的流程。 |
| 应检名单 | 创建批次时固定当前启用且有学生入住的寝室。之后入住/退宿不自动改变本周名单和历史完成率。 |
| 名单调整 | 系统管理员可带原因补入符合条件的寝室，或移出尚未评分的错误名单项；所有变更留痕，已评分寝室不能从名单移除。 |
| 批次状态 | 使用开放、关闭、停检三个管理状态；已检/未检/完成率独立计算，达到 100% 不代表关闭。 |
| 跨周与补录 | 普通录分只对当前周开放批次；跨周后关闭普通录入。系统管理员可带原因重开历史周补录，实际提交时间另存，不改变原周/月归属。 |
| 停检 | 系统管理员设置并记录原因；停检批次不计完成率考核、排名及趋势有效样本。已有成绩保留但不参与统计，恢复开放/关闭也须留痕。 |
| 评分版本 | 批次创建时绑定评分方案版本，本批次始终使用同一版本；新方案只供之后新建的批次采用。已被批次使用的标准不原地修改。 |
| 维度与权重 | 每个维度输入整数 0–100，权重允许两位小数且合计 100%；后端计算综合分并四舍五入到两位小数。 |
| 缺检 | 缺检不记零分，不进入平均值和排名；趋势显示空缺。 |
| 跨月归属 | 批次以该 ISO 周的周一作为统计归属日期；本周所有寝室归入同一月份。实际检查/提交时间单独保留。 |
| 月成绩 | 取归属该月的有效周成绩平均值，最终保留两位小数；至少一次有效记录才参与排名，展示实际参评周数。 |
| 同分 | 按最终展示精度的周期成绩实行竞赛排名 1、1、3；同分列表用寝室编号稳定排序，不影响并列名次。 |
| 草稿 | 服务端按录入人、批次、寝室保存；草稿不计成绩或进度，正式提交时重新校验批次、标准与重复评分。 |

## 7. 更正与整改

- 评分更正仅系统管理员可执行，必须填写原因；沿用原批次方案，保留同一正式记录、修改前后值、操作者与时间，统计展示更正后的有效值。
- 同时修改采用并发校验，避免后一操作无提示覆盖前一操作；批次关闭不禁止有审计的管理员更正。
- 整改使用单次综合分低于阈值触发，默认 60 分；不同时启用“连续两次”规则。阈值作为评分方案的一部分随版本固定，避免全局调整回写旧事件。
- 同寝室最多一条未关闭整改；后续低分不会重复生成，新的检查结果可在该寝室成绩中核对。
- 系统管理员和宿管部可记录跟进与核实结果，填写说明后关闭；后续合格不会静默自动关闭待核实事件。
- 更正使成绩变低时检查是否需要创建整改；更正使原触发成绩达标时，保留既有整改和跟进，提示触发成绩已更正，由有权管理角色核实后关闭，不自动抹除管理记录。

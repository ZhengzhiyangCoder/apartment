## 1. 问题陈述（Problem Statement）

本项目为高校宿舍管理系统本科毕业设计。需要把住宿资料、寝室报修、学生会宿管部卫生检查和卫生统计整合为一套实际可运行的电脑端系统。

核心问题是：学生无法方便追踪自己提交的维修请求；宿管部需要连续为多个寝室、多个楼栋录分；管理方需要在缺检、标准变更、同分和成绩纠错等情况下仍然获得可信的检查进度、统计与排行。

已有附件给出了整体方案，但部分功能在 P0/P1 与最终验收之间存在口径差异，检查批次、跨月归属和更正后的整改处理也需要明确。本规格将这些内容收敛为可实现、可验证的行为。

## 2. 解决方案与交付范围（Solution）

### 2.1 产品边界

交付一套中文电脑端 Web 系统，包含四种角色：系统管理员、宿舍管理员（学生会宿管部成员）、学生、维修人员。

- 宿舍管理员可以检查全校任意寝室，同一账号连续录入多间，也可跨楼栋。
- 学生可以查看当前寝室的成绩与历史趋势、当前楼栋排行榜，以及自己提交的报修。
- 系统围绕住宿管理、报修处理、卫生检查、统计排行与整改形成完整流程。
- 本期完成原 PRD 的 P0 与 P1。整改、更正审计、检查进度和服务端草稿均纳入交付。
- 主要界面支持 1920×1080 与 1366×768；仅要求桌面浏览器正常操作。

## 4. 实现与业务决策（Implementation Decisions）

### 4.1 系统结构

同一仓库内采用单个 Maven 后端工程与单个 Vue 前端工程，四角色共用前端。后端按账号权限（identity）、住宿（housing）、卫生检查（hygiene）、报修（repair）、工作台汇总（dashboard）五个业务模块组织；评分更正、整改、排名与卫生统计归 hygiene，统一审计及存储归支持能力。完整职责与文件位置见已确认的[工程结构 V1.0](../../docs/engineering-structure.md)。

| 项目 | 约定 |
|---|---|
| 后端 | Java 17、Spring Boot、Spring Security、MyBatis-Plus；具体兼容版本在实施阶段核验并锁定 |
| 前端 | Vue 3、TypeScript、Element Plus、ECharts |
| 数据库 | MySQL 8 系列，隔离的项目数据库及持久化数据卷 |
| 认证 | 浏览器经前端同源入口与 /api 代理访问后端，使用服务端 Session、HttpOnly 登录 Cookie、CSRF 防护 |
| 图片 | 后端受控本地存储；元数据入库，读取时检查工单权限 |
| 业务时区 | Asia/Shanghai |
| 页面风格 | 中文桌面工作台，以表格、表单、状态和检查进度为主 |
| 运行交付 | 前后端分离，仅要求本地实际启动验证；前端由本机 Node/npm 启动、后端由本机 Java/Maven 启动，Compose 仅启动项目 MySQL；提供本地配置与环境变量示例，不要求 Nginx 或云服务器部署 |

具体依赖版本在实施时按官方兼容要求固定，不使用未验证的版本组合。源码和交付文档不包含真实凭据或真实学生个人信息。

### 4.2 数据模型与持久化

附件列出的 18 张核心业务表作为建模输入，覆盖：用户、学生资料、楼栋/寝室/床位、入住历史、工单/图片/状态日志、评分方案/维度、批次/应检名单、正式评分/明细、更正日志、整改事件和关键操作日志。

服务端草稿暂存需要补充对应持久化结构。必要的版本号、时间、操作者、阈值快照和审计字段随正式数据库设计明确。表数不是验收目标，业务约束和可追溯性是验收目标。

必须由数据库与服务端共同保障：

- 同楼栋房号唯一，同寝室床位编号唯一。
- 一名学生最多一条当前住宿关系，一个床位最多一名当前入住学生。
- 同一 ISO 年周只有一个正式检查批次。
- 同一批次同一寝室只有一份当前有效正式评分；同一正式评分中各维度不能重复。
- 同寝室最多一条未关闭整改事件。
- 评分、调寝、工单流转、更正与相关日志应在同一业务事务内完成，失败时不得留下部分成功状态。
- 已引用的身份与业务资料保留历史，不以删除关联记录的方式绕过约束。

### 4.3 账号与住宿规则

- 账号由系统管理员创建和重置，不开放匿名注册；一个账号对应一个角色。
- 禁用账号不得登录或继续使用已有会话调用业务；修改角色后权限应按最新账号状态判断。
- 学生可以处于未入住状态。此时可登录并查看个人信息和自己提交过的工单，但不能新建寝室报修或查看寝室成绩、楼栋排行。
- 调寝同时结束原住宿关系并创建新关系；任一步失败，当前住宿保持原状。
- 账号、楼栋、寝室、床位停用前检查当前入住与未完业务，提示先处理相关事项；有历史引用的资料不硬删除。
- 学生成绩和趋势范围随当前住宿变化。调寝后可看新寝室历史，不再访问旧寝室成绩；本人历史报修继续可见，工单位置保持提交时的寝室。
- 学生排行榜只展示寝室编号、周期成绩、有效参评次数与名次，不披露个人姓名。

### 4.4 报修状态与责任

合法主流程：待分配 → 待处理 → 处理中 → 已完成。

取消分支：待分配或待处理 → 已取消。已完成、已取消均为终态；新的维修问题重新提交工单。

- 新建工单的提交人和寝室由服务端根据当前账号与住宿关系确定，不能由客户端任意指定。
- 派单只可选择有效、启用的维修人员，并记录派单人和时间。
- 进入处理中前允许有权管理角色重分配，必须填写原因；进入处理中后不提供普通重分配。
- 学生可以取消本人尚未进入处理中的工单；宿管部及系统管理员可按相同状态规则取消，均需原因。
- 维修人员只能开始或完成分配给自己的任务，不能处理他人的任务，不能从待处理直接跳到已完成。
- 完成维修必须填写处理说明；每次变更保留状态、操作者、时间与必要备注。
- 任何页面按钮、请求重放或接口参数篡改都不能绕过角色、归属和状态规则。

图片规则：JPG、PNG、WebP；每单最多 5 张，每张不超过 5 MB。校验实际内容、大小和数量；只允许具有该工单访问权的账号读取，不把磁盘路径直接暴露为下载地址。

### 4.5 评分方案与计算

- 每个维度输入整数 0–100；权重最多两位小数，启用时合计必须为 100%。
- 综合分为各维度分数与百分比权重的加权和，服务端使用精确十进制运算，最终四舍五入到两位小数。
- 客户端即时总分只用于预览，不能替代服务端计算；提交必须包含方案要求的全部且仅有这些维度。
- 修改已使用的维度、权重或整改阈值必须产生新版本；已绑定批次的标准不能原地修改。
- 同一时间只有一个供新批次采用的启用版本。批次创建时固定方案版本，后续启用新方案不会改变已有批次。
- 正式评分保存当时维度名称、权重、分数、总分和适用阈值等依据，历史记录不因配置变化回写。

### 4.6 周检批次与应检名单

- 使用 ISO 年周，周一至周日；跨年场景以 ISO 年而非直接使用自然年组成周标识。
- 默认准备当前周检查时创建批次；系统管理员与宿舍管理员都可以发起，重复或并发准备返回同一批次。
- 本期不提供提前创建未来周批次的业务入口。
- 创建批次时固定当前启用且有学生入住的应检寝室名单；之后入住/退宿不自动改变本周名单或旧周完成率。
- 系统管理员可以填写原因补入符合条件的寝室，或移出尚未评分的错误名单项；已经评分的寝室不能从名单移除。
- 名单调整保留前后差异、原因与操作者。进度以调整后的该批次名单计算，旧变更可追溯。
- 寝室不在应检名单时，不能直接提交正式评分。

批次管理状态为：**开放、关闭、停检**。

- 已检/未检/完成率是统计结果，与管理状态分开；达到 100% 不等于自动关闭。
- 默认普通录分面向当前周的开放批次。跨周后关闭旧批次的普通录入入口。
- 系统管理员可以带原因显式重开历史批次供宿管部补录；这是对默认跨周关闭的授权例外。补录记录实际提交时间，周/月仍归属原批次；不会被普通跨周处理再次立即关闭。
- 关闭状态禁止普通正式提交及草稿转正式；系统管理员仍可进行有审计的成绩更正。
- 停检由系统管理员设置并留痕；停检批次不参加完成率考核、排名和有效趋势样本。既有记录保留；恢复状态也必须留痕。
- 没有应检寝室时显示“暂无应检寝室”，不产生除零错误，也不显示具有误导性的完成率。

### 4.7 连续评分与草稿

- 宿管部进入指定开放批次，按楼栋/房号检索全校寝室，查看应检、已检和未检状态。
- “保存并下一间”必须在正式保存成功后才切换；下一间按当前筛选范围和房号顺序选择尚未评分的寝室。
- 校验失败、网络失败或并发冲突时保留当前输入并显示原因，不误跳转。
- 同批次同寝室不能新增第二份正式评分。多个账号或重复点击同时提交，只允许一份成功，其余得到明确冲突提示。
- 草稿按录入人、批次、寝室持久化，只对本人可编辑；草稿不计正式成绩、已检数量和排行榜。
- 草稿转正式时重新校验批次状态、名单、方案、分值与重复评分；不能绕过别人已提交的正式记录。
- 正式提交成功后清除对应个人草稿；关闭/停检批次的草稿可以查看，但不能直接发布。

### 4.8 成绩统计与排行

| 项目 | 统一口径 |
|---|---|
| 周成绩 | 该批次寝室唯一有效正式成绩，使用更正后的当前值 |
| 批次归属日 | 该 ISO 周的周一；实际检查/提交时间另存 |
| 月成绩 | 对归属当月各批次的有效周成绩取算术平均，最后保留两位小数 |
| 跨月周 | 本周所有寝室按同一批次周一归月，不按各自提交日期分月 |
| 最低参评次数 | 至少一次有效记录，未达到显示“未检查/数据不足”并不参与排名 |
| 缺检与停检 | 不记零分，不计入平均；趋势按缺失显示空缺 |
| 并列规则 | 按最终两位小数的周期成绩使用竞赛排名，例如 1、1、3 |
| 同分展示顺序 | 房号稳定排序；展示顺序不改变并列名次 |
| 楼栋平均成绩 | 对该楼栋所选周期内有有效周期成绩的寝室取平均，避免多参评寝室被重复加权 |
| 维度对比 | 只在相同方案版本、相同维度口径内比较；跨方案时分组展示，不把同名不同定义维度静默合并 |

学生只能查看当前楼栋排行。客户端传入其他楼栋或寝室标识时，服务端必须拒绝越权，不泄露无权访问的数据。

系统管理员和宿管部可查看全校或楼栋统计。榜单、图表和明细共用上述统计口径，同时显示周期和有效样本量。

楼栋平均成绩用于管理看板中的楼栋对比，结合参评寝室数量与检查进度展示；它不改变单间寝室成绩或学生看到的寝室名次，也不作为单间寝室整改的触发依据。

### 4.9 更正与整改

更正仅系统管理员可执行，必须说明原因；使用原批次方案重新校验和计算，保留同一正式评分的身份与完整前后记录。

- 更正不能改变原寝室或批次，不能创建第二份同周正式评分。
- 并发更正必须检测版本冲突，不能无提示地覆盖前一位操作者的修改。
- 更正后成绩明细、统计和排行反映当前有效值，审计仍保留原结果。

整改规则：

1. 单次综合分严格低于阈值时触发，默认阈值 60；不同时启用“连续两次低于阈值”规则。
2. 阈值随方案版本/批次固定，后续修改不能无痕改变原事件的触发依据。
3. 同寝室最多一条未关闭事件；后续低分不会重复生成未关闭事件。
4. 宿管部和系统管理员可以填写跟进、核实结果与关闭说明；关闭后新的检查低分可触发下一次事件。
5. 后续检查合格不自动关闭待核实事件，管理角色核实后关闭。
6. 更正使成绩低于阈值时，检查是否需要生成或复用未关闭事件。
7. 更正使原触发成绩达标时，保留整改和跟进，提示“触发成绩已更正”，由有权管理角色核实后关闭；不自动删除历史记录。
8. 整改是系统内业务列表与状态，不产生公告、短信或微信推送。

### 4.10 公开接口和交互约定

- 公开接口按身份、住宿、报修、评分标准、周检、正式评分、统计、整改和审计组织；操作使用本规格的领域术语。
- 所有业务写入均执行服务端参数、角色、数据归属及状态校验；只读查询不隐式产生新的业务写入。
- 列表具备查询条件和分页；服务端限制分页大小，并对查询参数和排序字段采用白名单。
- 错误应区分未登录、无权限、参数错误、业务冲突及服务器失败，向界面提供可理解的信息，不返回堆栈或敏感内部内容。
- 前端提供加载、空数据、错误与成功反馈；请求进行中避免重复操作，失败时保留可恢复的表单内容。
- 表格与图表在两种目标桌面尺寸下可操作，不因横向溢出遮挡关键按钮；无权角色不能通过手工输入页面地址访问业务数据。

## 5. 测试与验收决策（Testing Decisions）

### 5.1 测试边界

主要从**公开 HTTP API** 验证权限、业务状态、持久化结果、错误及统计；连接真实、隔离的 MySQL。通过查询接口观察写入结果，不依赖内部方法名称或服务调用次数。

其次从**实际浏览器界面**验证四角色关键路径、连续评分、失败保留输入和桌面布局。数据库迁移另外验证能在干净的目标 MySQL 上执行并启动应用。

当前没有既有业务代码或测试惯例可复用。测试以本规格的明确示例和期望值为依据，不把实现表达式重新计算一遍充当预期结果。规格审核后再编写或执行实现测试。
